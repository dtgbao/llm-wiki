The scenario: the agent escalates the wrong cases

Your support agent has 55% first-contact resolution. The target is 80% (sample Q3). The logs show two errors:

Easy case   standard damage replacement, photo attached    → the agent ESCALATES   ✗
Hard case   the customer wants a policy exception          → the agent RESOLVES    ✗

The problem is unclear decision boundaries. The agent does not know what an escalation case is.

Escalation triggers

EscalateDo not escalate only because of
1. The customer asks for a humanA complex case that the policy covers
2. A policy exception or gap: the policy is ambiguous or silentNegative sentiment
3. The agent cannot make meaningful progressA low self-reported confidence score

Why sentiment and confidence fail. Both are unreliable proxies for case complexity. An angry customer can have a simple case. The agent is frequently confident on the hard cases that it handles incorrectly.

Four situations, four actions

SituationAction
"Let me talk to a human."Escalate immediately. Do not investigate first
The customer is frustrated but did not ask for a human. The issue is within the agent's capabilityAcknowledge the frustration and offer the resolution. Escalate if the customer repeats the preference
Competitor price match. The policy covers only own-site price adjustmentsEscalate: the policy is silent on this request
get_customer returns three matchesAsk for an additional identifier. Do not select by heuristic

The fix: explicit criteria with few-shot examples

# Before: vague
"Escalate when the case is too complex or you are not confident."

# After: explicit criteria + examples (Lesson 11)
"""
Escalate when: the customer asks for a human; the policy does not cover
the request; you cannot make progress.
Resolve when: the policy covers the request, also if it has many steps.

<example>
customer:  My lamp arrived broken. Photo attached.
action:    RESOLVE. Standard damage replacement. The policy covers it.
</example>
<example>
customer:  Another shop sells it for $20 less. Match that price.
action:    ESCALATE. The policy covers only our own price changes.
</example>
<example>
customer:  This is the third time! Where is my refund?
action:    RESOLVE. Acknowledge the frustration. The refund is within
           your capability. Escalate only if the customer asks again.
</example>
"""

This is the proportionate first response. A separate classifier model is over-engineered. Sentiment analysis and a confidence threshold measure the wrong thing. When the agent escalates, it sends a structured handoff summary (Lesson 3).

The scenario: "97% accurate, remove the review"

An extraction pipeline has 97% overall accuracy. The team wants to stop human review. Look at the segments first:

Document type          Volume    Accuracy
typed invoices         9,000     99.5%
handwritten receipts     800     71%      ← hidden by the aggregate
contracts                200     88%
───────────────────────────────────────
overall               10,000     97%

An aggregate metric can mask poor performance on a specific document type or field.

The human review design

StepWhat you do
1. Validate by segmentMeasure accuracy by document type and by field before you automate
2. Field-level confidenceThe model outputs a confidence score for each field
3. CalibrateUse a labeled validation set to find the threshold where the score predicts correctness
4. RouteLow confidence, or an ambiguous or contradictory source → human review. This uses the limited reviewer capacity well
5. Sample continuouslyStratified random sampling of high-confidence extractions. It measures the error rate and finds novel error patterns
# 3. Calibrate: at which score is the field correct 99% of the time?
for threshold in (0.70, 0.80, 0.90, 0.95):
    accepted = [x for x in validation_set if x.confidence >= threshold]
    print(threshold, accuracy(accepted))          # pick the threshold that meets the target

# 4. Route
def route(extraction):
    if extraction.conflict_detected or any(f.confidence < THRESHOLD[f.name] for f in extraction.fields):
        return "human_review"
    return "auto_accept"

# 5. Sample the auto-accepted items, the same share from each document type
for doc_type in DOC_TYPES:
    sample = random.sample(auto_accepted[doc_type], k=50)
    send_to_reviewer(sample)                      # error rate + novel patterns

Confidence: three lessons, one rule. A raw self-reported score is unreliable (Lesson 11, and escalation above). A score becomes useful only after calibration against labeled data. Then it routes review attention. It never replaces the sampling in step 5.
