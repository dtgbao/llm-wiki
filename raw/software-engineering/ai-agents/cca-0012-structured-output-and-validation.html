Structured output with a tool

Tool use with a JSON schema is the most reliable approach for schema-compliant output. It eliminates JSON syntax errors (exam guide 4.3). You define an extraction tool. The schema is the tool's input. You read the data from the tool_use block.

tools = [{
  "name": "extract_invoice",
  "description": "Record the fields of one invoice.",
  "strict": True,
  "input_schema": {
    "type": "object",
    "properties": {
      "invoice_number":  {"type": "string"},
      "po_number":       {"type": ["string", "null"]},     # source can lack it
      "category":        {"enum": ["goods", "services", "other", "unclear"]},
      "category_detail": {"type": ["string", "null"]},     # text when "other"
      "stated_total":    {"type": "number"},
      "calculated_total":{"type": "number"},               # sum of line items
      "conflict_detected": {"type": "boolean"}
    },
    "required": ["invoice_number", "po_number", "category", "category_detail",
                 "stated_total", "calculated_total", "conflict_detected"],
    "additionalProperties": False
  }
}]

response.content → [{"type": "tool_use", "name": "extract_invoice",
                     "input": { ...your structured data... }}]

Source: Claude API: tool use and Structured outputs.

tool_choice

SettingModel behaviorUse it when
{"type": "auto"}Can return text and call no toolA text answer is acceptable
{"type": "any"}Must call a tool. It chooses which oneSeveral extraction schemas; unknown document type
{"type": "tool", "name": "extract_metadata"}Must call that named toolOne extraction must run first, before enrichment

Guide vs docs. The exam follows the table above. The docs add one limit: the newest models (for example Claude Opus 5.5 and Sonnet 5.5) reject any and tool with a 400 error. Manual extended thinking rejects them too. There, use auto with strict: true, or structured outputs (output_config.format).

Syntax errors and semantic errors

                         A strict schema...
Syntax    missing brace, wrong type, missing required field      ELIMINATES
Semantic  line items do not sum to the total                     DOES NOT PREVENT
          a value is in the wrong field                          DOES NOT PREVENT
          a value is fabricated for a required field             DOES NOT PREVENT

Schema design

ProblemSchema design
The source can lack the information; the model fabricates a valueMake the field nullable, not a required value
A case is ambiguousAdd the enum value "unclear"
New categories appear laterEnum with "other" + a detail string field
Source formats are inconsistent (dates, currency)Put format normalization rules in the prompt, next to the strict schema

Validation and retry

extract ──► validate in code ──► pass ──► done
                 │
                 └─ fail ──► follow-up request with:
                              1. the original document
                              2. the failed extraction
                              3. the specific validation errors
                             ("calculated_total 410.00 ≠ stated_total 440.00")
A retry worksA retry does not work
Format mismatch (date, currency)The information is absent from the source
Structural output errorThe information is only in an external document that you did not provide
Values in the wrong field; sums that do not match

Self-correction fields. Extract calculated_total next to stated_total. Your code compares them and flags a discrepancy. Add a conflict_detected boolean for inconsistent source data.

Feedback loop. Add a detected_pattern field to each finding. It records the code construct that triggered the finding. When developers dismiss findings, you group the dismissals by pattern and find the false positive patterns (exam guide 4.4).
